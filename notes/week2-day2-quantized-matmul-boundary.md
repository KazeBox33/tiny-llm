## 要解决的问题

Python 的 `quantized_linear` 已经会展平激活的前导维度、整理连续存储，并调用 C++ 扩展。词嵌入的 `as_linear` 也已经使用压缩权重计算词表输出，无须重写这些接口。

但是，C++ 入口原先只检查转置方式、四位编码和每组 128 个权重。Metal 内核按激活的类型读取缩放值和偏移值，并按 uint32 读取压缩权重。如果数组类型或尺寸不匹配，调用方仍然能够创建非法的延迟计算图。

首先加入回归测试：BF16 激活搭配 FP32 缩放值，应在调用原生函数时报告错误。修复前，该测试失败于 `DID NOT RAISE`。测试没有执行非法 GPU 计算。

## 本次改动

在 `src/extensions/src/quantized_matmul.cpp` 中，创建计算图之前检查：

- 激活、压缩权重、缩放值、偏移值均为二维数组。
- 激活使用 FP16 或 BF16；缩放值和偏移值与激活类型一致。
- 压缩权重使用 uint32。
- 激活形状为 `[M,N]`，N 能被 128 整除。
- 压缩权重形状为 `[K,N/8]`。
- 缩放值和偏移值形状均为 `[K,N/128]`。

通过检查后，仍然返回形状 `[M,K]`、类型与激活相同的延迟数组。入口检查只使用数组描述，不把 GPU 张量复制回 CPU。

在 GPU 实际执行前，补充缩放值和偏移值的连续存储检查。此时输入的物理布局已经确定。已有 Python 包装函数会调用 `mx.contiguous` 整理四个输入；直接调用原生接口时，非连续的缩放值或偏移值会明确报错。

没有改变 Metal 计算公式、线程安排、现有 CPU 实现及 Python 包装函数。

## 参照计算的排错记录

初始测试使用 MLX 0.29.1 的 `mx.quantized_matmul` 作为数值参照，五个输出通道的最后一个通道出现较大差异。随后用 NumPy 独立解包，并以 FP32 计算点积，得到：

| 形状及输出 | NumPy FP32 | 自写 GPU BF16 | MLX GPU BF16 |
| --- | ---: | ---: | ---: |
| A=[1,256]、逻辑权重=[5,256]，最后一个通道 | -21.25378 | -21.25 | -13.0 |
| A=[1,256]、逻辑权重=[8,256]，第 5 个通道 | -21.25378 | -21.25 | -21.25 |

因此，新测试使用独立 NumPy 计算，并按输出类型舍入作为数值参照，不依赖上述小尾块场景的库输出。测试中的解包仅用于小尺寸正确性验证，模型实际推理仍使用压缩权重。这项观察限于当前版本和该输入，未修改或完整诊断 MLX 上游内核。
